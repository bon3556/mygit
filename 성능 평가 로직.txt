1. 개요


이 코드는 생성된 SQL(gen_sql)이 자연어 질문의 의미에 맞는지 평가하는
고정밀 NL2SQL semantic validator입니다.
단순히 SQL 문자열이 그럴듯한지만 보는 것이 아니라,
다음 요소를 함께 고려하여 최종 판정을 내립니다.

자연어 질문(user_question_final)
실제 카탈로그에서 재생성한 테이블 정보(tables_info)
원본 카탈로그로부터 만든 구조화된 스키마 제약(structured_schema_constraints)
생성된 SQL(gen_sql)
보조 참고용 semantic_form


즉, 이 validator의 핵심 목적은 다음과 같습니다.

생성된 SQL이 질문 의미를 올바르게 답하고 있는지를,
실제 스키마/카탈로그 제약까지ㄹ 반영하여 고정밀하게 판정하는 것

2. 이 validator의 철학


이 코드는 일반적인 “문자열 비교형 SQL 평가기”와 다릅니다.
핵심 철학은 다음과 같습니다.

2.1 질문 의미가 1차 기준


최종 correctness는 기본적으로 자연어 질문의 의미를 따라야 합니다.
즉:

질문이 무엇을 요구하는지
SQL이 실제로 무엇을 계산하는지


를 비교합니다.

2.2 실제 스키마 제약이 매우 중요


단, 자연어적으로 비슷해 보여도 실제 스키마에 맞지 않는 값/컬럼/포맷을 사용하면 올바르지 않다고 봅니다.
예:

카테고리 컬럼에 실제 저장값이 PROJECTLEADER인데 SQL이 '프로젝트 리더'로 비교
날짜 컬럼 포맷이 YYYY-MM-DD HH:MM:SS인데 SQL이 LIKE '20230731%'로 잘못 비교
존재하지 않는 컬럼명 사용


이런 경우는 강한 negative signal로 취급합니다.

2.3 semantic_form은 정답 기준이 아님


이 validator는 semantic_form을 절대 정답 기준으로 사용하지 않습니다.
중요 원칙:

semantic_form raw는 correctness ground truth가 아님
semantic_form은 참고용/보조적 개념 힌트만 제공
최종 판정은 질문 의미 + 실제 스키마 제약 기준으로 결정


즉 평가용 SQL이 semantic_form과 표면적으로 다르더라도, 질문 의미를 정확히 답하고 실제 스키마 제약을 만족하면 정답일 수 있습니다.

2.4 카탈로그 기반 재생성 정보 사용


입력 파일에 이미 tables_info가 있더라도, validator는 원본 카탈로그로부터 다시 readable tables_info를 재생성해서 사용합니다.
즉 검증 시 사용하는 테이블 정보는 입력 데이터에 저장된 임의 텍스트가 아니라 원본 카탈로그 기준의 최신/신뢰 가능한 정보입니다.

3. 전체 목적


이 validator의 목표는 다음과 같습니다.

원본 카탈로그로부터 검증용 테이블 정보를 재생성하고
구조화된 스키마 제약을 만들고
질문 의도를 추출하고
SQL이 실제로 무엇을 하는지 요약하고
초기 correctness 판정을 내리고
defense review와 prosecution review를 거쳐
최종 adjudication을 내리고
틀린 경우에만 에러 타입까지 분류하는 것


즉 단순 one-shot 판정이 아니라, 다단계 의미 분석 + 논쟁 구조 + 최종 판결 형태의 평가기입니다.

10. 구조화된 스키마 제약 생성
주요 함수
build_structured_schema_constraints(...)


이 함수는 카탈로그 subset을 읽어 validator가 강하게 참조할 structured schema constraints를 만듭니다.
structured_schema_constraints는 원본 카탈로그에서 현재 질문에 관련된 테이블(table_list)만 추출한 뒤, 컬럼 존재 여부, categorical/code 컬럼의 허용 sample value, datetime 컬럼의 format hint 등을 검증에 바로 사용할 수 있도록 구조화한 스키마 규칙 정보이다.
이 정보는 build_structured_schema_constraints() 함수에서 생성되며, 결과에는 known_columns, column_details, categorical_columns, datetime_columns, code_like_columns 등이 포함된다.
이후 validator는 이 구조화된 스키마 제약을 이용해 SQL이 존재하지 않는 컬럼을 사용하는지, categorical/code literal이 실제 stored representation과 맞는지, 날짜/시간 literal 또는 pattern이 schema format hint와 일치하는지를 검사한다.

10.4 categorical 컬럼 판정


다음 조건을 이용해 categorical 컬럼인지 추정합니다.

sample value 개수가 너무 많지 않음
datetime 성격이 아님
숫자 컬럼 힌트가 아님


그리고 일부 categorical 컬럼은
strict_value_match_required=True 로 분류합니다.
이 의미는:

SQL filter value가 sample 기반 domain evidence와 다르면 강한 오류 신호로 본다


예:

상태코드
역할코드
구분값
Y/N 플래그가 아닌 명시적 enum 컬럼
10.5 datetime 컬럼 판정


다음 힌트를 이용합니다.

sample에 YYYY-MM-DD
sample에 HH:MM:SS
설명에 날짜/일시
컬럼명이 _DATE, _DT, _TS 등으로 끝남


이를 통해 날짜/시간 포맷 mismatch를 잡아냅니다.

11. SQL filter와 schema compliance evidence 구축
주요 함수
extract_sql_simple_filter_predicates(...)
build_schema_compliance_evidence(...)


이 단계는 생성된 SQL의 filter literal이
실제 schema evidence와 부합하는지를 강하게 점검합니다.

11.1 SQL filter predicate 추출


지원하는 filter 형태:

=, !=, <>, >, >=, <, <=, LIKE
IN (...)
BETWEEN 'x' AND 'y'


예를 들어 SQL에서 다음을 추출합니다.

어떤 컬럼을 비교했는지
어떤 operator를 썼는지
어떤 literal을 썼는지
11.2 unknown identifier 탐지


SQL에서 뽑은 identifier 후보를 known_columns와 비교해 존재하지 않는 컬럼 후보를 찾습니다.
결과는 다음 필드로 저장됩니다.

sql_unknown_identifier_candidates


이 값이 있으면 강한 negative signal입니다.

11.3 categorical value mismatch 검사


strict categorical 컬럼의 경우, SQL filter value가 allowed sample values와 다르면 mismatch로 기록합니다.
예:

schema sample values: ["PROJECTLEADER", "T/L"]
SQL filter: '프로젝트 리더'


→ mismatch
결과는 다음에 저장됩니다.

schema_categorical_value_mismatches


이 값이 있으면 schema-based incorrect 가능성이 매우 높습니다.

11.4 datetime format mismatch 검사


예를 들어 schema sample이 YYYY-MM-DD HH:MM:SS인데 SQL이 LIKE '20230731%' 같은 패턴을 쓴다면 mismatch 가능성을 기록합니다.
결과는 다음에 저장됩니다.

schema_datetime_format_mismatches


이 역시 강한 negative signal입니다.

11.5 strict signal 요약


schema mismatch가 발견되면 다음 같은 strict signal을 남깁니다.

schema_categorical_value_mismatch
schema_datetime_format_mismatch


이 값은 이후 adjudication 단계에서 강한 증거로 사용됩니다.

1. Attribute-related Errors


컬럼(속성)과 관련된 오류입니다.

1) attribute_mismatch


잘못된 컬럼을 사용한 경우

의도한 컬럼이 아닌 다른 컬럼을 조회/조건/집계에 사용한 경우입니다.
예:
정답: SELECT customer_id
오류: SELECT customer_name


즉, 컬럼은 있는데 선택을 잘못한 경우입니다.

2) attribute_redundancy


불필요한 컬럼이 추가된 경우

정답에는 필요 없는 컬럼을 더 조회하거나 조건에 추가한 경우입니다.
예:
정답: SELECT customer_id
오류: SELECT customer_id, customer_name


즉, 쓸데없는 컬럼이 더 들어간 경우입니다.

3) attribute_missing


필요한 컬럼이 빠진 경우

정답 SQL에 있어야 할 컬럼이 누락된 경우입니다.
예:
정답: SELECT customer_id, customer_name
오류: SELECT customer_id


즉, 반드시 있어야 하는 컬럼이 빠진 경우입니다.

2. Table-related Errors


테이블과 JOIN 관련 오류입니다.

4) table_mismatch


잘못된 테이블을 사용한 경우

의도한 테이블이 아닌 다른 테이블을 쓴 경우입니다.
예:
정답: FROM orders
오류: FROM customers


즉, 테이블 선택이 틀린 경우입니다.

5) table_redundancy


불필요한 테이블이 추가된 경우

정답에는 필요 없는 테이블을 JOIN하거나 FROM에 포함한 경우입니다.
예:
정답: FROM orders
오류: FROM orders, customers


즉, 안 써도 되는 테이블을 더 쓴 경우입니다.

6) table_missing


필요한 테이블이 빠진 경우

정답 SQL에서 사용해야 하는 테이블이 누락된 경우입니다.
예:
정답: FROM orders o JOIN customers c ON o.customer_id = c.customer_id
오류: FROM orders o


즉, 필수 테이블이 빠진 경우입니다.

7) join_condition_mismatch


JOIN 조건이 잘못된 경우

JOIN은 했지만 연결 조건(ON)이 틀린 경우입니다.
예:
정답: ON o.customer_id = c.customer_id
오류: ON o.order_id = c.customer_id


즉, 테이블 연결 방식이 틀린 경우입니다.

8) join_type_mismatch


JOIN 종류가 잘못된 경우

INNER JOIN, LEFT JOIN, RIGHT JOIN 등의 종류가 정답과 다른 경우입니다.
예:
정답: LEFT JOIN
오류: INNER JOIN


즉, JOIN 방식 자체가 틀린 경우입니다.

3. Value-related Errors


값 자체와 형식 관련 오류입니다.

9) value_mismatch


비교값/상수값이 잘못된 경우

조건에 들어가는 값이 정답과 다른 경우입니다.
예:
정답: WHERE year = 2023
오류: WHERE year = 2022


즉, 값이 틀린 경우입니다.

10) data_format_mismatch


데이터 형식/표현 방식이 잘못된 경우

값은 비슷해 보이지만 형식이 맞지 않는 경우입니다.
예:
날짜 형식 오류: '2023-01-01' 대신 '20230101'
문자열/숫자 형식 오류
YYYYMM이어야 하는데 YYYY-MM 사용


즉, 값의 포맷이 틀린 경우입니다.

4. Operator-related Errors


연산자 관련 오류입니다.

11) comparison_operator_mismatch


비교 연산자가 잘못된 경우

=, !=, >, <, >=, <=, IN, LIKE 등의 비교 방식이 틀린 경우입니다.
예:
정답: price > 100
오류: price >= 100


즉, 비교하는 방식이 틀린 경우입니다.

12) logical_operator_mismatch


논리 연산자가 잘못된 경우

AND, OR, NOT 등이 정답과 다르게 사용된 경우입니다.
예:
정답: WHERE age > 20 AND gender = 'F'
오류: WHERE age > 20 OR gender = 'F'


즉, 조건을 묶는 논리가 틀린 경우입니다.

5. Condition-related Errors


WHERE, HAVING 등의 조건 자체와 관련된 오류입니다.

13) explicit_condition_missing


명시적으로 써야 할 조건이 빠진 경우

정답 SQL에 특정 조건이 분명히 있어야 하는데 누락된 경우입니다.
예:
정답: WHERE status = 'ACTIVE'
오류: 조건 없음


즉, 필수 조건이 빠진 경우입니다.

14) explicit_condition_mismatch


조건 내용이 잘못된 경우

조건은 있는데, 그 조건식이 정답과 다릅니다.
예:
정답: WHERE amount > 1000
오류: WHERE amount > 500


즉, 조건 자체가 틀린 경우입니다.

15) explicit_condition_redundancy


불필요한 조건이 추가된 경우

정답에는 없는 조건을 추가해서 결과를 더 제한한 경우입니다.
예:
정답: WHERE region = 'KR'
오류: WHERE region = 'KR' AND status = 'ACTIVE'


즉, 쓸데없는 조건이 더 들어간 경우입니다.

16) implicit_condition_missing


명시적으로 쓰진 않았지만 사실상 필요한 조건이 빠진 경우
이건 조금 헷갈릴 수 있는데,
정답 SQL에 직접 적혀 있진 않아도 질문 의도상 반드시 반영돼야 하는 조건이 빠진 경우입니다.

예:
질문: “2023년 한국 매출”
SQL: WHERE year = 2023만 있고 country = 'KR'가 없음


즉, 질문 의미상 당연히 있어야 하는 숨은 조건이 빠진 경우입니다.

6. Function-related Errors


함수 사용 관련 오류입니다.

17) aggregate_function_mismatch


집계 함수가 잘못된 경우

SUM, COUNT, AVG, MAX, MIN 등을 잘못 사용한 경우입니다.
예:
정답: SUM(sales)
오류: AVG(sales)


즉, 집계 방식이 틀린 경우입니다.

18) window_function_mismatch


윈도우 함수가 잘못된 경우

ROW_NUMBER(), RANK(), DENSE_RANK(), SUM() OVER(...) 같은 윈도우 함수가 틀린 경우입니다.
예:
정답: ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC)
오류: RANK() OVER (...)


즉, 윈도우 함수 종류나 OVER 조건이 틀린 경우입니다.

19) datetime_function_mismatch


날짜/시간 함수가 잘못된 경우

날짜 처리 함수가 정답과 다르게 쓰인 경우입니다.
예:
정답: DATE_TRUNC(order_date, MONTH)
오류: EXTRACT(YEAR FROM order_date)


즉, 날짜를 다루는 방식이 틀린 경우입니다.

20) conversion_function_mismatch


형변환 함수가 잘못된 경우

CAST, CONVERT, SAFE_CAST 등을 잘못 사용한 경우입니다.
예:
정답: CAST(amount AS INT64)
오류: CAST(amount AS STRING)


즉, 자료형 변환이 틀린 경우입니다.

21) math_function_mismatch


수학 함수가 잘못된 경우

ROUND, CEIL, FLOOR, ABS 등 수학 함수가 틀린 경우입니다.
예:
정답: ROUND(price, 2)
오류: FLOOR(price)


즉, 수치 계산 함수가 틀린 경우입니다.

22) string_function_mismatch


문자열 함수가 잘못된 경우

SUBSTR, CONCAT, TRIM, UPPER, LOWER 등을 잘못 쓴 경우입니다.
예:
정답: UPPER(name)
오류: LOWER(name)


즉, 문자열 처리 방식이 틀린 경우입니다.

23) conditional_function_mismatch


조건 함수가 잘못된 경우

CASE WHEN, IF, COALESCE, NULLIF 같은 조건 함수 사용이 틀린 경우입니다.
예:
정답: CASE WHEN score >= 60 THEN 'PASS' ELSE 'FAIL' END
오류: 조건이 다르거나 함수가 바뀜


즉, 조건 분기 함수가 틀린 경우입니다.

7. Clause-related Errors


SQL 절(Clause) 관련 오류입니다.

24) clause_missing


필요한 절이 빠진 경우

WHERE, GROUP BY, HAVING, ORDER BY, LIMIT 같은 절이 누락된 경우입니다.
예:
정답: GROUP BY category
오류: GROUP BY 없음


즉, SQL 구조의 한 부분이 빠진 경우입니다.

25) clause_redundancy


불필요한 절이 추가된 경우

정답에 없는 절이 추가된 경우입니다.
예:
정답: SELECT * FROM t
오류: SELECT * FROM t ORDER BY id


즉, 필요 없는 절이 더 들어간 경우입니다.

8. Subquery-related Errors


서브쿼리 관련 오류입니다.

26) subquery_missing


필요한 서브쿼리가 빠진 경우

정답에서는 서브쿼리가 필요한데, 이를 생략한 경우입니다.
예:
정답: WHERE id IN (SELECT ...)
오류: 서브쿼리 없이 단순 비교


즉, 필수 서브쿼리가 없는 경우입니다.

27) subquery_mismatch


서브쿼리 내용이 잘못된 경우

서브쿼리는 있는데 내부 로직이 틀린 경우입니다.
예:
안쪽 SELECT 컬럼이 다름
WHERE 조건이 다름
GROUP BY/HAVING이 다름


즉, 서브쿼리 구조나 내용이 틀린 경우입니다.

28) partial_query


쿼리가 불완전한 경우

SQL이 중간에 끊겼거나 일부만 작성된 경우입니다.
예:
SELECT name FROM
WHERE amount >


즉, 쿼리가 완성되지 않은 경우입니다.

9. Other Errors


그 외 오류입니다.

29) asc_desc_mismatch


정렬 방향이 잘못된 경우

ASC와 DESC가 바뀐 경우입니다.
예:
정답: ORDER BY sales DESC
오류: ORDER BY sales ASC


즉, 오름차순/내림차순이 틀린 경우입니다.

30) distinct_mismatch


DISTINCT 사용이 잘못된 경우

정답은 DISTINCT가 필요한데 없거나, 필요 없는데 들어간 경우입니다.
예:
정답: SELECT DISTINCT customer_id
오류: SELECT customer_id


즉, 중복 제거 여부가 틀린 경우입니다.

31) other


기타 분류하기 어려운 오류

위 범주에 명확히 들어가지 않는 오류입니다.
예:
DBMS 문법 차이
복합적인 의미 오류
애매한 케이스


즉, 기타 예외적인 오류입니다.

한눈에 보는 아주 짧은 요약
attribute: 컬럼이 틀림 / 더 있음 / 빠짐
table: 테이블이나 JOIN이 틀림
value: 값이나 값 형식이 틀림
operator: 연산자(=, AND 등)가 틀림
condition: 조건이 틀림 / 빠짐 / 더 있음
function: 함수(SUM, CAST, DATE_TRUNC 등)가 틀림
clause: WHERE, GROUP BY, ORDER BY 같은 절이 틀림
subquery: 서브쿼리가 틀림 / 빠짐
other: 그 외


즉 단순 correct/incorrect를 넘어서 어떤 종류의 오류인지까지 구조적으로 분류합니다.

13. Semantic evidence 구성
주요 함수
build_semantic_evidence(...)


Semantic evidence는 생성된 SQL, semantic_form, table_list, 그리고 구조화된 스키마 제약을 비교하여 코드 기반으로 생성한 중간 증거 정보이다.
먼저 SQL을 정규화한 뒤, SQL에서 실제 사용된 테이블, 식별자, 문자열 literal, join/group by/aggregate 같은 구조 정보를 추출한다.
동시에 semantic_form에서 의미상 필요한 테이블, 컬럼, filter value를 추출하여 SQL과 비교한다.
이후 SQL을 structured_schema_constraints와 대조하여, 존재하지 않는 컬럼 사용 여부, categorical/code literal 불일치, datetime literal/pattern 포맷 불일치 여부를 검사한다.
마지막으로 이러한 비교 결과를 SemanticEvidence 객체에 모아 used_tables, missing_tables, sql_filter_predicates, schema_categorical_value_mismatches, schema_datetime_format_mismatches, suspicious_signals 등의 필드로 저장한다.

13.1 포함되는 정보
normalized_gen_sql
sql_nonempty
used_tables
semantic_tables
missing_tables
extra_tables
sql_literals
semantic_literals
semantic_filter_specs
semantic_columns
sql_identifier_candidates
semantic_sql_column_overlap
semantic_sql_column_only_in_semantic
semantic_sql_column_only_in_sql
has_join, has_group_by, has_order_by, has_distinct
has_subquery, has_aggregate, has_window
schema compliance evidence
suspicious_signals
13.2 suspicious signal 예시


다음과 같은 signal을 만듭니다.

empty_sql
reference_gap:semantic_table_not_used
reference_gap:semantic_literal_not_found_in_sql
reference_gap:semantic_join_shape_difference
reference_gap:semantic_groupby_shape_difference
reference_gap:semantic_orderby_shape_difference
date_prefix_like_detected
schema_strict:categorical_value_mismatch
schema_strict:datetime_format_mismatch
schema_strict:unknown_identifier_candidate_exists


즉 validator는 단순 LLM 호출 전에 이미 많은 정적 evidence를 확보해 둡니다.

14. Prompt 기반 다단계 평가 구조


이 validator는 한 번에 “맞다/틀리다”를 묻지 않고, 여러 단계로 나누어 의미를 분석합니다.
각 단계는 서로 다른 역할을 가집니다.

15. semantic_form concept 추출
주요 함수
llm_extract_semantic_form_concepts(...)
목적


semantic_form을 표면 문자열이 아니라 의미 개념 수준으로 요약합니다.
중요 원칙:

semantic_form은 ground truth 아님
exact column/literal/join은 약한 힌트
business meaning, relation meaning, ratio definition clue, time scope clue 등만 추출


출력 예시 구조:

required_concepts
required_constraints
required_relations
acceptable_variants
weak_surface_hints


즉 semantic_form을 correctness 기준으로 쓰는 것이 아니라, 후속 리뷰를 위한 보조 개념 정보로 변환합니다.

16. Question intent 추출
주요 함수
llm_extract_question_intent(...)
목적


자연어 질문이 요구하는 의미를 구조화합니다.
출력 필드 예시:

task_type
target_entity
answer_grain
grouping_dimensions
requested_outputs
filters
time_constraints
ranking_requirements
ratio_requirements
allowed_ambiguities
must_not_change
이 단계에서 중요한 점
16.1 질문이 primary source of truth


question intent는 validator 전체에서 가장 중요한 기준 중 하나입니다.

16.2 경계 조건 ambiguity 처리


특히 다음 표현은 애매성 허용 대상으로 처리합니다.

이후
이전
after
before
since
until


예:

2023-01-01 이후는 > 또는 >= 모두 허용 가능
2023-01-01 이전은 < 또는 <= 모두 허용 가능


즉 validator는 이런 boundary ambiguity를 후속 판단에 반영합니다.

16.3 ratio 질문은 numerator/denominator를 명시


비율/점유율 질문은

numerator
denominator
denominator scope


를 구조적으로 설명하도록 유도합니다.

17. SQL semantic summary 추출
주요 함수
llm_extract_sql_semantic_summary(...)
목적


생성된 SQL이 실제로 무엇을 의미하는지 요약합니다.
중요한 점:

correctness 판정은 아직 하지 않음
SQL이 실제로 하는 일을 의미 수준에서 설명
출력 내용 예시
selected_dimensions
grouping_dimensions
metric_expressions
filters
time_filter_analysis
join_analysis
aggregation_analysis
window_analysis
schema_compliance_summary
definite_sql_meaning
possible_risks
ambiguous_points


즉 이 단계는 SQL을 “정답인지 아닌지” 판단하는 것이 아니라,
SQL이 실제로 어떤 차원으로 집계하고, 어떤 값을 필터링하고, 어떤 위험이 있는지를 설명하는 단계입니다.

17.1 join_analysis


join_analysis는 다음과 같은 내용을 포함합니다.

has_join
join_purpose_summary
join_multiplicity_risk
why


특히 join_multiplicity_risk는 매우 중요합니다.
가능한 값:

low
medium
high
unknown


즉, 조인으로 인해 다대다 매칭 / 중복 합산 / 과집계 위험이 있는지를 설명합니다.

17.2 aggregation_analysis


집계 관련 구조입니다.
포함 내용:

has_aggregate
aggregation_scope
post_aggregation_ranking_or_filter
possible_preaggregation_needed
why


예를 들어:

브랜드별 집계를 하는지
집계 후 top-N을 자르는지
pre-aggregation이 필요한데 바로 join해서 중복합산 위험이 있는지


같은 내용을 담습니다.

why


즉 SQL에 ROW_NUMBER() OVER (...) 같은 구조가 있으면 그 의미를 별도로 설명합니다.

schema evidence와 SQL의 부합 정도를 요약합니다.

18. Initial correctness judge
주요 함수
llm_initial_correctness_judge(...)


이 단계에서 처음으로 SQL이 correct / incorrect / uncertain 중 무엇인지를 판정합니다.

18.1 판정 기준


이 prompt의 핵심 원칙은 다음과 같습니다.

질문이 primary source of truth
readable tables_info는 business context 제공
structured schema constraints는 강한 제약
semantic_form_concepts는 참고만 가능
semantic_form과 표면적으로 다르다는 이유만으로 fail 금지
의미가 동일하고 schema 제약을 만족하면 정답 가능
ambiguity가 허용되면 incorrect보다 correct/uncertain 우선


즉 이 단계는 매우 보수적으로 incorrect를 주도록 설계되어 있습니다.

18.2 strict schema compliance rule


아래는 strong negative signal입니다.

schema에 없는 categorical/code literal 사용
schema 포맷과 맞지 않는 datetime literal/pattern 사용
존재하지 않는 컬럼 사용


즉 자연어적으로 비슷하더라도 실제 저장형 값/포맷을 어기면 incorrect 가능성이 큽니다.

18.3 tolerance rule


반대로 아래는 지나치게 harsh하게 incorrect를 주지 않도록 허용합니다.

1) 시간 경계 ambiguity
이후, 이전 같은 표현은 > / >= 또는 < / <=의 ambiguity 허용
2) LIMIT 허용
per-entity listing / exploratory query에서 LIMIT 100 같은 것은 exhaustive requirement가 없다면 단독 오류로 보지 않음
3) 필요한 join 허용
질문에 명시되지 않은 테이블이 join되었더라도 요청된 속성/필터를 가져오기 위해 필요한 join이면 허용 가능
4) sample mismatch 과잉 해석 금지
schema sample 값이 일부 다르다고 해서 join incompatibility를 단정하지 않음


즉 이 validator는 false positive를 줄이는 방향으로 초기 판정을 설계했습니다.

18.4 출력 구조


이 단계의 출력은 다음을 포함합니다.

verdict: correct | incorrect | uncertain
confidence
material_semantic_difference
question_sql_alignment
false_positive_check
possible_false_positive_patterns
reason
18.5 question_sql_alignment


질문과 SQL의 정렬 상태를 세부 축별로 설명합니다.
포함 항목:

target_entity_alignment
metric_alignment
filter_alignment
grouping_alignment
time_boundary_alignment
ratio_alignment
join_aggregation_alignment
schema_compliance_alignment


즉 “왜 맞다/틀리다”를 단일 문장이 아니라 의미 요소별로 나누어 설명합니다.

18.6 false_positive_check


이 항목은 initial incorrect 판정이 과도한지 점검하기 위한 체크리스트입니다.
예:

semantic_form_surface_overreach
equivalent_joined_column_possible
boundary_ambiguity_allows_sql

즉 initial judge 단계부터 “내가 혹시 과하게 틀렸다고 본 건 아닌가?”를 같이 점검합니다.

19. Defense review
주요 함수
llm_defense_review(...)


이 단계는 initial judgment가 **너무 가혹했는지(false positive 가능성)**를 검토하는 역할입니다.
즉 initial verdict가 incorrect 또는 uncertain일 때, “사실 맞는 SQL일 수도 있지 않은가?”를 방어 측 관점에서 따져봅니다.

19.1 defense review의 역할


이 단계는 무조건 정답으로 뒤집는 것이 아니라, 다음 질문을 던집니다.

initial judgment가 너무 strict했나?
semantic_form surface mismatch를 과하게 본 건 아닌가?
join이 실제로 필요한 상황 아닌가?
boundary ambiguity를 놓친 건 아닌가?
LIMIT을 과하게 벌점 준 건 아닌가?
partial sample mismatch를 join failure로 과잉 해석한 건 아닌가?


즉 false positive 교정기 역할을 합니다.

19.2 defense가 특히 완화하는 케이스
1) semantic_form 표면 mismatch 과대평가


semantic_form과 다르더라도 business meaning이 같으면 허용 가능

2) joined table의 동일 의미 컬럼 사용


같은 의미를 가진 컬럼을 joined table에서 가져오는 경우 허용 가능

3) 이후/이전 경계 ambiguity


시간 경계는 명시적으로 strict/inclusive가 없으면 허용 폭을 둠

4) count 해석 차이


건수/개수/수는 COUNT vs COUNT(DISTINCT) ambiguity가 있을 수 있음

5) ratio denominator scope 오판


분모 범위를 잘못 비난했는지 재검토

6) LIMIT 과잉 벌점


list/query 스타일 질문에서는 LIMIT이 단독 오류가 아닐 수 있음

7) 필요한 join 과잉 벌점


다른 테이블에서만 제공되는 속성/필터를 가져오기 위한 join이면 허용 가능

19.3 defense review 출력
initial_verdict_supported
possible_false_positive
false_positive_patterns
best_argument_for_correctness
remaining_real_concerns
revised_verdict
confidence
reason


즉 initial judgment를 유지할지, 더 관대하게 바꿔야 할지에 대한 방어 측 의견을 냅니다.

20. Prosecution review
주요 함수
llm_prosecution_review(...)


이 단계는 defense와 반대로, initial judgment가 **너무 느슨했는지(false negative 가능성)**를 검토합니다.
즉 initial verdict가 correct 또는 uncertain일 때, “사실 틀린 SQL일 수도 있지 않은가?”를 검사합니다.

20.1 prosecution review의 역할


이 단계는 다음을 따집니다.

essential filter가 빠진 건 아닌가?
잘못된 categorical value를 쓴 건 아닌가?
ratio 정의가 틀린 건 아닌가?
denominator scope가 틀린 건 아닌가?
aggregation grain이 잘못된 건 아닌가?
join multiplication 때문에 잘못된 sum/count가 된 건 아닌가?
ranking metric이 틀린 건 아닌가?
schema에 없는 컬럼을 쓴 건 아닌가?


즉 false negative 탐지기 역할입니다.

20.2 prosecution이 중점적으로 보는 오류
1) missing essential filter


질문에 반드시 있어야 할 조건이 SQL에 없을 때

2) wrong stored categorical value


schema-supported stored value와 다른 literal 사용

3) wrong ratio definition


비율 질문인데 numerator / denominator가 잘못됨

4) wrong denominator scope


예를 들어 “전체 판매대수 대비”인데 분모 scope가 잘못된 경우

5) wrong aggregation grain


브랜드 수준 질문인데 모델 수준 row를 직접 합산해서 중복되는 경우

6) join multiplication


join 후 count/sum이 중복 합산되는 경우

7) unknown column usage


실제 schema에 없는 컬럼 사용

8) unsupported datetime literal/pattern


schema 포맷과 어긋나는 날짜/시간 literal 사용

20.3 prosecution review 출력
initial_verdict_supported
possible_false_negative
material_risk_patterns
best_argument_for_incorrectness
revised_verdict
confidence
reason


즉 initial 판정이 너무 느슨하지 않았는지를 검토합니다.

22. Heuristic post-adjudication adjustment
주요 함수
heuristic_post_adjudication_adjustment(...)


LLM 기반 final adjudication 이후에, 일부 대표적인 false positive를 rule-based로 한 번 더 완화합니다.
즉 이 함수는 후처리형 안전장치입니다.

22.1 왜 필요한가


LLM이 final adjudication까지 했더라도 특정 패턴에서는 여전히 too harsh하게 incorrect를 줄 수 있습니다.
예:

이후/이전 경계 해석
listing query의 LIMIT
필요한 join에 대한 과잉 벌점
date prefix LIKE 패턴


그래서 마지막으로 heuristic correction을 적용합니다.

22.2 강한 schema violation은 완화하지 않음


다음이 있으면 heuristic soften을 하지 않습니다.

schema_categorical_value_mismatches
schema_datetime_format_mismatches
sql_unknown_identifier_candidates


즉 실제 schema 위반은 heuristic로 덮지 않습니다.

22.3 경계 ambiguity 완화


질문에 이후, 이전, after, before, since, until이 있고 strict boundary가 명시되지 않았다면

> vs >=
< vs <=


차이만으로 incorrect를 주는 것을 완화할 수 있습니다.

22.4 LIMIT 완화


질문이 listing / per-entity / exploratory 스타일이면 LIMIT N은 단독으로 material error가 아닐 수 있습니다.
예:

“각 모델별로 보여줘”
“목록을 알려줘”
“출력해줘”


이런 질문은 exhaustive completeness가 명시되지 않으면 LIMIT만으로 incorrect 처리하지 않도록 완화합니다.

22.5 join 과잉 벌점 완화


join이 존재한다고 해서 자동으로 의심하지 않습니다.
특히:

다른 테이블에만 존재하는 요청 속성/필터를 가져오기 위한 join
sample mismatch만 있는 join


은 incorrect를 완화할 수 있습니다.

22.6 date prefix LIKE 완화


예를 들어 timestamp-like 문자열 컬럼에서 LIKE '20230731%'가 하루 전체를 의미할 수도 있습니다.
schema strong negative가 없는 경우, 이런 패턴은 incorrect → uncertain으로 완화할 수 있습니다.

주요 함수
llm_error_typing(...)


이 단계는 오직 final verdict가 incorrect일 때만 수행됩니다.
즉 이 단계는 “맞는지 틀린지”를 다시 논의하지 않고, 이미 틀렸다고 확정된 SQL의 오류 타입만 분류합니다.

23.1 입력 정보

즉 최종 판정까지의 모든 의미 정보와 schema evidence를 반영합니다.

23.2 분류 원칙
표면 mismatch가 아니라 실제 semantic/schema mismatch를 분류
error localization이 잘못되었으면 여기서 교정 가능
여러 카테고리를 허용하되, 정말 필요한 경우에만 multi-label

23.3 대표적인 매핑 예시

잘못된 ratio/aggregation 의미 → Function-related Errors
잘못된 grouping key → Attribute-related Errors
잘못된 table / join logic → Table-related Errors

즉 incorrect SQL은 왜 틀렸는지뿐 아니라 어떤 유형의 오류인지까지 정리됩니다.

37. 이 validator의 핵심 장점


이 코드의 장점을 요약하면 다음과 같습니다.

37.1 semantic_form 의존도를 낮춤


많은 validator가 semantic_form을 사실상 정답처럼 취급하는데, 이 코드는 그렇지 않습니다.
즉:

semantic_form raw ≠ ground truth
question meaning + real schema constraints가 더 중요


이 철학은 실제 SQL correctness 판단에 더 현실적입니다.

37.2 원본 카탈로그 기준 검증


입력에 있는 오래된 tables_info를 그대로 신뢰하지 않고, 원본 카탈로그에서 다시 readable tables_info를 만듭니다.
즉 validator가 사용하는 schema context의 신뢰도가 높습니다.

37.3 schema strictness 반영


이 validator는 특히 다음을 엄격히 봅니다.

categorical/code literal 불일치
datetime literal/pattern 불일치
unknown/hallucinated column


즉 “의미상 비슷해 보인다”만으로 correct를 주지 않고, 실제 stored representation도 중요하게 반영합니다.

37.4 false positive / false negative 균형


한 번의 판정으로 끝내지 않고:

initial judge
defense review
prosecution review
final adjudication
heuristic adjustment


단계를 거칩니다.
즉 너무 strict하거나 너무 lenient한 판정을 줄이도록 설계되어 있습니다.

37.5 explanation-rich 결과


최종 결과는 단순 verdict가 아니라 다음을 모두 포함합니다.

question intent
SQL semantic summary
schema compliance evidence
initial / defense / prosecution / final reasoning
error categories


즉 결과를 사람이 리뷰하고 분석하기에 매우 좋습니다.

39. 핵심 포인트 요약


이 validator의 핵심을 한 줄씩 정리하면 다음과 같습니다.

39.1 질문 의미와 실제 스키마를 함께 본다


question meaning만 보는 것도 아니고, semantic_form만 보는 것도 아니며, 질문 + schema + SQL 의미를 함께 평가합니다.

39.2 semantic_form은 참고용이다


semantic_form과 SQL이 표면적으로 다르더라도, 질문 의미를 정확히 답하고 schema를 만족하면 정답일 수 있습니다.

39.3 categorical/date/code representation을 엄격히 본다


자연어적으로 비슷해도 실제 저장값 표현이 다르면 incorrect가 될 수 있습니다.

39.4 false positive를 줄이기 위한 방어 구조가 있다


defense review, heuristic adjustment를 통해 과잉 incorrect 판정을 완화합니다.

39.5 false negative도 잡기 위한 prosecution review가 있다


겉보기엔 맞아 보여도 중요 filter/ratio/aggregation grain이 틀리면 incorrect로 잡아냅니다.

39.6 결과가 explainable하다


최종 verdict만 주는 것이 아니라, 왜 그렇게 판정했는지 구조적으로 남깁니다.

40. 마무리


이 validator는 단순한 SQL 판정기가 아니라,
질문 의미 / SQL 의미 / 실제 카탈로그 제약 / 다단계 리뷰를 결합한 고정밀 semantic validation agent입니다.
즉 현재 버전의 핵심은 다음 한 줄로 요약할 수 있습니다.

생성된 SQL이 질문의 의미를 실제 스키마 제약 안에서 올바르게 답하는지를, 다단계 의미 분석과 리뷰 구조를 통해 평가하는 validator

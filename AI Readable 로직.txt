1. 개요


본 파이프라인은 EAP 메타데이터 및 실데이터 샘플을 기반으로, 사람이 이해하기 쉬운 데이터 카탈로그 정보를 자동 생성하는 작업이다.
생성 대상은 크게 아래 4가지이다.

샘플 데이터 조회: SAMPLE_DATA
컬럼 설명 생성: LLM_COL
샘플 데이터 의미 설명 생성: LLM_SMP
테이블 설명 생성: LLM_TB_DESC




2. 전체 파이프라인 구조
현재 실행 순서


run_pipeline() 기준 실행 흐름은 아래와 같다.

BigQuery에서 메타데이터 조회
GetSampleDataProcessor 실행
AIReadableColumnsProcessor 실행
SmpColumnsProcessor 실행
AIReadableTablesProcessor 실행
현재 구조의 특징


각 프로세스는 기본적으로:

parquet 파일을 입력으로 읽고
특정 컬럼을 생성/업데이트한 뒤
parquet 파일로 저장한다.


각 단계는 이전 단계 결과를 입력으로 받아야 자연스러운 순차 처리가 되는데, 현재 실행 코드에서는 일부 경로가 하드코딩되어 있어 완전한 체인 구조는 아니다.
즉, 운영 시에는 아래 구조로 정리하는 것이 바람직하다.
ExamplePython
 
sample_processor.file_process(input_base_file, sample_output_file)
column_processor.file_process(sample_output_file, col_output_file)
smp_processor.file_process(psnl_output_file, smp_output_file)
table_processor.file_process(smp_output_file, final_output_file)

3. 주요 컬럼 설명
원본 메타 컬럼
DATASET_NAME: 데이터셋명
TABLE_NAME: 테이블명
BIZ_KOR_DESC: 업무 설명
BIZ_DOMAIN_LV1_KOR_NAME: 업무 도메인
TAB_LOGICAL_NAME: 테이블 논리명
TAB_COL_NAME: 컬럼명
TAB_COL_COMMENT: 컬럼 주석/설명
TAB_COL_DATA_TYPE: 컬럼 데이터 타입
BIZ_META_STATUS_CODE: 메타 상태 코드
PSNL_COL_NAME: 원천 개인정보 여부
생성 컬럼
SAMPLE_DATA: BigQuery 샘플 데이터
LLM_COL: LLM 기반 컬럼 설명
LLM_SMP: LLM 기반 샘플 데이터 의미 설명
LLM_PSNL: LLM 기반 개인정보 여부
LLM_TB_DESC: LLM 기반 테이블 설명
비고: 예외/오류/보완 메모
4. 공통 처리 규칙
4.1 재처리 기준


대부분 프로세스는 특정 컬럼 값이 아래 조건일 때 재처리한다.

NaN
"new_data"
"NEW_DATA"


현재는 실패값(Error, querytimeout, nodata 등)을 재처리 대상으로 넓게 잡지 않고 있다.
즉 현재 정책은:

신규 데이터 중심 재처리


과거에는 더 넓은 실패값도 포함했던 흔적이 있으나 현재 주석 처리되어 있다.

4.2 비고 컬럼 관리


비고 컬럼은 에러, 응답 누락, 후처리 실패 등의 메모를 누적 기록하는 용도이다.
공통 함수:

ensure_note_column()
append_note()


형식:
Example
 
기존메시지 | 신규메시지

4.3 병렬 처리


각 프로세스는 ThreadPoolExecutor를 사용한다.

샘플 조회: row 단위 병렬
컬럼 설명: table 단위 병렬
샘플 설명: table 단위 병렬
테이블 설명: table 단위 병렬


비용, 카운트, 체크포인트 저장은 lock 기반으로 제어한다.

5. 프로세스별 상세 설명
5-1. GetSampleDataProcessor
목적


실제 BigQuery 데이터에서 컬럼별 대표 샘플값을 조회하여 SAMPLE_DATA를 채우는 프로세스이다.
이 단계는 후속 단계(LLM_COL, LLM_SMP)의 핵심 입력이 된다.

입력


필수 컬럼:

DATASET_NAME
TABLE_NAME
TAB_COL_NAME


보조 컬럼:

SAMPLE_DATA
비고
출력
SAMPLE_DATA
비고
처리 대상


현재는 아래 row가 대상이다.

SAMPLE_DATA가 null
SAMPLE_DATA == new_data
내부 동작 방식
1) 대상 BigQuery 테이블명 생성


원천 메타의 DATASET_NAME, TABLE_NAME을 바탕으로 BigQuery view명을 생성한다.
기본 규칙:
ExamplePython
 
V_{DATASET_NAME without _}_{TABLE_NAME}

예외:

dataset이 _로 끝나면 _가 두 번 들어가는 형태 처리
2) 테이블 존재 여부 확인


INFORMATION_SCHEMA.TABLES 조회
없으면:

tablenotfound
3) 컬럼 존재 여부 확인


INFORMATION_SCHEMA.COLUMNS 조회
없으면:

colnotfound
4) 샘플 데이터 조회


해당 컬럼의 값 빈도를 계산하여 상위 20개 값을 문자열로 반환한다.
출력 예:
Example
 
"A"|"B"|"C"

또는
Example
 
20250101|20250102|20250103

5) 예외 처리
결과 없음 → nodata
timeout → querytimeout
처리 실패 → Error + 비고
특징
샘플은 랜덤 샘플이 아니라 상위 빈도 샘플
후속 설명 생성 시 대표값 이해에 유리
길이 제한: 최대 200000자
프롬프트 사용 여부


이 프로세스는 LLM 프롬프트를 사용하지 않는다. BigQuery 조회 기반 처리만 수행한다.

운영 시 주의사항
BigQuery view naming rule 변경 시 대량 실패 가능
SAMPLE_DATA가 이후 모든 LLM 품질에 직접 영향
nodata, tablenotfound, colnotfound는 후속 단계에서 별도 문구로 치환됨

column_comment

샘플값은 의미 추론 보조용이지, 의미를 새로 만들기 위한 근거가 되면 안 된다.

반드시 아래 형식을 따르도록 요구한다.

  "COLUMN_A": ["설명"],

특징:

JSON 외 다른 텍스트 금지
inst_template vs inst_template_v2

inst_template_v2는 조금 더 간결한 버전


실사용 시 하나로 통일하는 것이 관리상 좋다.

이상 시:

누락 컬럼 → Error
비정상 값 → Error
비고에 상세 원인 기록


예:

5-3. PsnlColumnsProcessor
목적


개인정보 포함 여부를 판단하여 LLM_PSNL 값을 생성하는 프로세스로 보인다.
현재 제공된 실행 예시에서는 실제 호출되지 않지만, 설계상 SmpColumnsProcessor 이전에 수행되는 것이 자연스럽다.

예상 입력
TAB_COL_NAME
TAB_COL_COMMENT
SAMPLE_DATA
예상 출력
LLM_PSNL = Y / N
사용 프롬프트
psnl_prompt_template


이 프롬프트는 컬럼이 개인정보(PII)인지 판별하는 목적이다.
입력:
Example
 
column_name | column_comment | sample_data

출력:
ExampleJSON
 
{
  "COLUMN_NAME_A": "Y",
  "COLUMN_NAME_B": "N"
}

프롬프트 핵심 규칙
1) 우선 메타정보로 판단
컬럼명
컬럼설명


만으로도 명확히 개인정보면 Y
즉:

PHONE_NO
EMAIL_ADDR
CUSTOMER_NAME 같은 컬럼은 샘플을 보지 않아도 판단 가능
2) 메타상 개인정보가 아니라고 보이면 샘플까지 확인


메타 정보만으로 N 같더라도 샘플에 실제 개인정보 패턴이 있으면 재검토한다.

3) PII 예시를 풍부하게 제공


프롬프트에 아래 범주가 매우 상세히 정의되어 있다.

이름/ID
주민번호/여권번호
전화번호/이메일
주소
금융정보
생년월일/성별
계정/인증정보
기기 식별자
고객/거래 정보
간접식별자
민감정보


즉, 단순 개인정보뿐 아니라 간접 식별 가능 정보까지 포함한다.

후속 단계와의 관계


SmpColumnsProcessor에서는 아래 조건이면 LLM_SMP를 빈값으로 저장한다.

PSNL_COL_NAME == "Y"
LLM_PSNL == "Y"


즉 개인정보 컬럼은 데이터 예시 설명을 의도적으로 생성하지 않음.

운영 시 주의사항
PSNL_COL_NAME과 LLM_PSNL 충돌 시 우선순위 정책 필요
false positive / false negative 검증 체계 필요
샘플 데이터 기반 개인정보 감지는 보안 이슈 고려 필요
5-4. SmpColumnsProcessor
목적


SAMPLE_DATA를 기반으로 컬럼 값의 실제 의미/형태를 사람이 읽기 쉬운 형태로 바꿔 LLM_SMP에 저장한다.
예:

20250101|20250102 → YYYYMMDD 형태의 날짜
1|2|3 → 정수 값
01|02|03 + 이름컬럼 존재 → {"01": "정상", "02": "해지", ...}
입력
TAB_COL_NAME
TAB_COL_COMMENT
TAB_COL_DATA_TYPE
SAMPLE_DATA
PSNL_COL_NAME
LLM_PSNL
출력
LLM_SMP
비고
내부 동작 방식
1) 개인정보 컬럼 제외


다음이면 빈 문자열 저장:

PSNL_COL_NAME == Y
LLM_PSNL == Y


즉 개인정보 컬럼은 샘플 해석을 하지 않는다.

2) 샘플 조회 실패값 치환
tablenotfound → 테이블 미발견
colnotfound → 컬럼 미발견
nodata → 조회 결과 데이터 미존재
공백 샘플 → 데이터 전체 공백으로 기재
3) enum 후보 탐지


컬럼명이 아래 패턴이면 enum 후보로 간주한다.

*_CD
*_CODE


그리고 같은 테이블에 아래가 있으면 매핑 대상:

*_NM
*_NAME


예:

STATUS_CD ↔ STATUS_NM
TYPE_CODE ↔ TYPE_NAME
4) enum 직접 생성


BigQuery에서 code-name 쌍을 조회하여 dict 형태 문자열 생성
예:
Example
 
{"01": "정상", "02": "대기", "03": "종료"}

5) enum이 아니면 LLM 판별


컬럼별 샘플 데이터를 보고 실제 타입을 판별한다.

업무 목적

TAB_COL_NAME

행 단위 grain을 알 수 없음
분포를 알 수 없음
컬럼 역할 정도만 추론 가능


이 점을 LLM이 오해하지 않도록 강하게 제약함

추정
샘플 기준
불일치 가능


등으로 표기하도록 요구한다.

5) 출력 포맷 강제

출력은 반드시 아래 구조만 허용한다.
Example
 
[정의 및 목적]
...

[상세 설명]
- 핵심 정보 요약: ...
- 데이터 품질/주의사항: ...
- 활용 예시: ...

프롬프트에서 이 형식을 매우 강하게 제한하고 있으며, 다음을 금지한다.
Output, 결과, 설명 같은 추가 제목
markdown code block
불필요한 공백 라인
섹션 추가 생성
테이블명을 제목처럼 번역하는 행위

즉, 최종 결과는 데이터 카탈로그 UI나 문서에 바로 붙여 넣을 수 있는 정형 텍스트를 목표로 한다.
6) 데이터 품질/주의사항 작성 규칙

프롬프트의 중요한 제약 중 하나는 데이터 품질/주의사항 항목에 반드시 근거 기반 문장을 쓰도록 한 점이다.
예를 들어 아래와 같은 형태를 기대한다.
(COL_A: 'Y|N|y'처럼 대소문자 혼재)
(COL_B 코드 'A01'인데 설명은 'A-01'로 표기)
샘플 기준 근거 확인 불가

중요한 점은:
경고성 문구를 추측으로 만들면 안 됨
반드시 LLM_SMP, LLM_COL, origin_desc 등 입력 근거에서 확인 가능해야 함
근거가 없으면 무리해서 품질 이슈를 만들지 않고 샘플 기준 근거 확인 불가로 작성

즉, 이 프롬프트는 그럴듯한 품질 경고를 만드는 것보다, 근거 있는 주의사항을 짧게 쓰는 것을 우선한다.
7) origin_desc 반영 규칙

이 프롬프트에서 origin_desc는 상당히 중요하다.
단순 참고용이 아니라, 가능하면 유지해야 하는 공식 설명 자산으로 취급한다.
반영 우선 대상:
테이블의 업무 목적
관리 대상
활용 목적
대표 컬럼과 의미

특히 origin_desc에 컬럼명이 직접 들어있으면,
[상세 설명] - 핵심 정보 요약에 우선 반영하도록 요구한다.
예를 들어 원본 설명에:
요청번호(REQUEST_NUMBER)
활동유형코드(ACTIVITY_TYPE_CODE)
요청금액(REQUEST_AMOUNT)

이 있다면, 샘플 데이터와 명백히 충돌하지 않는 한 최종 결과에서도 살려야 한다.
이 규칙의 의미는 다음과 같다.
LLM이 기존 설명을 무시하고 새로 “창작”하지 않도록 방지
이미 검토된 업무 설명 자산을 최대한 활용
샘플 기반 추론보다 기존 설명 자산을 우선 보존
8) sample_values 해석 규칙

프롬프트에서 가장 중요한 오해 방지 장치 중 하나이다.
입력으로 들어가는 sample_values는 실제 테이블 row가 아니다.
아래 3개 컬럼으로 구성된 컬럼 요약 테이블이다.
TAB_COL_NAME
LLM_SMP
LLM_DESC 또는 LLM_COL

즉 이 데이터로는 알 수 없는 것이 많다.
알기 어려운 것:
실제 row grain
행 단위 의미
컬럼 간 실제 조합 관계
row-level distribution

알 수 있는 것:
어떤 컬럼들이 있는지
각 컬럼의 대략적 의미
각 컬럼의 값 형태
테이블이 어떤 업무 도메인일 가능성이 높은지

그래서 프롬프트는 LLM에게:
컬럼 패턴
날짜 패턴
코드/상태/수량/금액 패턴
기존 설명

정도를 바탕으로 보수적으로 추론하라고 지시한다.
출력 예시 해석

최종적으로 기대하는 산출물은 아래와 같은 스타일이다.
Example
 
[정의 및 목적]
'SALES_ORDER_HIST' 테이블은 주문 이력 및 상태 변경 정보를 관리하기 위한 데이터로 추정된다. 기존 설명 기준 주문번호, 주문일자, 상태코드 등을 통해 주문 처리 현황과 변경 이력을 추적하기 위한 목적으로 활용된다.

[상세 설명]
- 핵심 정보 요약: 주문번호, 주문일자, 고객번호, 상태코드, 처리금액을 통해 주문 현황과 처리 이력을 파악한다.
- 데이터 품질/주의사항: 상태값 표기가 혼재될 가능성이 있다(STATUS_CD: '01|1|001' 형태 샘플 기준).
- 활용 예시: 주문 처리 모니터링 및 상태 변경 원인분석, 운영 리포트 작성에 활용할 수 있다.
운영 시 주의사항
LLM_SMP, LLM_COL 품질이 낮으면 테이블 설명 품질도 직접 저하된다.
테이블 설명은 테이블 단위 1개 문장 세트로 생성되며, 같은 테이블의 모든 row에 동일하게 들어간다.
현재는 max_workers=1이라 비교적 안정적이지만 느릴 수 있다.
컬럼 수가 많고 설명이 긴 테이블은 프롬프트 길이가 길어질 수 있다.
개선 포인트
너무 큰 테이블은 대표 컬럼만 추려서 넣는 전략 가능
origin_desc와 생성 설명 간 diff 비교 로직 추가 가능
품질 이슈 문구를 rule-based로 먼저 만들어주고 LLM이 다듬게 하는 방식도 가능

7. 프로세스 간 의존관계

각 프로세스는 완전히 독립적이지 않다.
앞 단계 결과가 다음 단계 입력 품질에 직접 영향을 준다.
의존관계
GetSampleDataProcessor
SAMPLE_DATA 생성
AIReadableColumnsProcessor
SAMPLE_DATA를 참고해 LLM_COL 생성
PsnlColumnsProcessor
컬럼명/샘플을 보고 LLM_PSNL 생성
SmpColumnsProcessor
SAMPLE_DATA, LLM_PSNL 기반으로 LLM_SMP 생성
AIReadableTablesProcessor
LLM_SMP, LLM_COL, BIZ_KOR_DESC로 LLM_TB_DESC 생성
품질 전이 특성
샘플 데이터가 부정확하면 컬럼 설명도 흔들림
컬럼 설명과 샘플 설명이 부정확하면 테이블 설명 품질이 급격히 저하됨
개인정보 판별이 누락되면 민감 컬럼의 샘플 설명이 생성될 수 있음

즉, 앞 단계 품질이 뒤 단계 품질을 결정하는 구조이다.

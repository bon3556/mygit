 1.NL2SQL 성능 측정용 질문/정답셋 생성 코드 인수인계 자료
=====
목적


이 코드는 NL2SQL 모델의 성능을 측정하기 위한 평가셋을 자동으로 생성하는 파이프라인이다.
평가셋은 자연어 질문과 그에 대응하는 정답 SQL로 구성된다.
최종 산출물에는 다음 정보가 포함된다.

user_question

LLM이 최초 생성한 원본 질문
[TABLES: ...] 접두어가 포함되어 있음
어떤 테이블을 기준으로 생성된 질문인지 추적하기 위한 용도

user_question_final

최종 사용자 질문
질문 리라이팅 및 코드값 자연어화가 반영된 질문
실제 평가 시 사용자 질문으로 사용할 수 있는 문장

semantic_form

질문 의도를 구조화한 중간 표현
SELECT, FILTER, GROUP BY, JOIN, ORDER BY 등의 정보를 JSON 형태로 보관
gold_sql 생성과 검증의 기준이 됨

gold_sql

semantic_form을 기준으로 생성된 정답 SQL
NL2SQL 모델이 생성한 SQL과 비교할 기준 정답


최종 결과는 시스템별 Excel 파일과 전체 통합 Excel 파일로 저장된다.

 4. 테이블명 생성 방식
=====


카탈로그에 있는 DATASET_NAME과 TABLE_NAME을 조합해서 ic360_table_name을 생성한다.
생성 규칙은 다음과 같다.

prefix로 v_를 붙인다.
DATASET_NAME에서 언더스코어를 제거하고 소문자로 변환한다.
TABLE_NAME을 소문자로 변환한다.
두 값을 언더스코어로 연결한다.


예시는 다음과 같다.

DATASET_NAME: New GDMi(전사수요관리시스템)
TABLE_NAME: SAMPLE_TABLE
생성 결과: v_new gdmi(전사수요관리시스템)_sample_table


실제 데이터에서는 DATASET_NAME 값에 따라 v_로 시작하는 ic360용 테이블명이 생성된다.
이 ic360_table_name은 이후 모든 단계에서 기준 테이블명으로 사용된다.

prompt table block
join 후보 생성
semantic_form
gold_sql
SQL 검증

 5. 주요 실행 설정
=====


5.1 날짜 suffix
현재 코드에서는 다음 값이 사용된다.

now_date = 260421


이 값은 출력 파일명에 포함된다.
예시:

question_260421_New GDMi(전사수요관리시스템).xlsx
question_total_260421.xlsx


5.2 SQL Dialect
현재 코드는 BigQuery 기준으로 실행된다.

DIALECT = BigQuery


지원 가능한 dialect는 다음 두 가지다.

BigQuery
PostgreSQL


입력값은 다음과 같이 정규화된다.

bigquery, bq -> BigQuery
postgresql, postgres, pg -> PostgreSQL


5.3 실행 대상 시스템
현재 실행 대상 시스템은 다음 리스트로 지정한다.

list_system_name


현재 코드에서는 아래 시스템만 활성화되어 있다.

New GDMi(전사수요관리시스템)


다른 시스템을 추가하려면 list_system_name에 시스템명을 추가하거나 주석을 해제하면 된다.
5.4 출력 디렉토리
출력 경로는 다음 규칙으로 생성된다.

/data001/bonsang.koo/2026/ai_readable/eap/question_{now_date}


현재 now_date가 260421이므로 실제 경로는 다음과 같다.

/data001/bonsang.koo/2026/ai_readable/eap/question_260421


5.5 병렬 처리
시스템별 처리는 ThreadPoolExecutor로 병렬 수행한다.
현재 설정은 다음과 같다.

max_workers = 10


단, Azure OpenAI rate limit이 발생할 수 있으므로 시스템 수가 많거나 호출량이 많을 경우 max_workers를 3~5 수준으로 낮추는 것이 안전하다.

 8. Stage 0.5 - 테이블 목적 기반 그룹핑
=====


관련 함수:

build_table_purpose_summary_df
group_tables_by_purpose_similarity
build_complementary_table_groups
propose_join_candidate_sets_by_purpose_groups


역할:
전체 테이블을 한 번에 LLM에 넣는 대신, 테이블 목적 설명을 기준으로 관련 있는 테이블끼리 묶는다.
그룹핑은 크게 두 가지 방식으로 수행된다.
첫 번째는 유사 목적 그룹이다.
테이블 목적 설명에 포함된 키워드를 보고 다음과 같은 bucket으로 분류한다.

sales

매출, 판매, sales, order, demand 등

product

제품, 모델, SKU, product, PLM 등

customer

고객, 회원, 구독, 사용자 등

supply

공급, 재고, 물류, SCM, inventory 등

service

서비스, 케어, 수리, 상담, CS 등

development

개발, 프로젝트, 설계, 인증, 시험 등

organization

조직, 법인, 사업부, 국가, 지역 등

code_master

코드, 기준정보, 마스터, 분류 등

status_history

상태, 이력, 로그, 변경 등

other

위 기준에 해당하지 않는 경우


두 번째는 보완 관계 그룹이다.
업무적으로 조인이 자연스러운 조합을 별도로 만든다.
예시는 다음과 같다.

sales + product
sales + organization
sales + code_master
customer + organization
customer + status_history
service + customer
supply + product
supply + organization
development + product
status_history + code_master


이 단계의 목적은 단순히 이름이 비슷한 테이블이 아니라, 실제 분석 질문에서 함께 쓰일 가능성이 높은 테이블 세트를 만들기 위함이다.

=====
9. Stage 1 - Join 후보 세트 생성
=====


관련 함수:

propose_join_candidate_sets
propose_join_candidate_sets_by_purpose_groups


사용 prompt:

MAKE_JOIN_CANDIDATES_PROMPT


역할:
LLM이 테이블 block을 보고 조인 가능성이 있는 테이블 세트를 제안한다.
각 후보 세트는 보통 2~4개 테이블로 구성된다.
LLM이 판단하는 기준은 다음과 같다.

동일하거나 유사한 컬럼명이 있는지 확인
*_ID, *_NO, *_CD, CODE, KEY, SEQ 등 조인 키 후보 확인
값 예시 형태가 유사한지 확인
fact 테이블과 dimension 또는 master 테이블 조합인지 확인
상태/코드/분류 해석이 필요한 조합인지 확인


Join 후보 세트에는 다음 정보가 포함된다.

set_id

후보 세트 ID
예: s01, s02

tables

해당 세트에 포함된 테이블 목록

join_key_candidates

조인 가능성이 있는 컬럼 쌍 목록

confidence

high, medium, low 중 하나
조인 가능성 및 업무적 자연스러움에 대한 신뢰도


confidence 기준은 다음과 같다.

high

컬럼명이 거의 동일하거나 동의어 수준
값 형태가 유사
fact/dimension 보완 관계가 자연스러움

medium

컬럼명이 유사하거나 약간 변형
값 형태가 어느 정도 유사
업무상 함께 볼 가능성이 있음

low

추정은 가능하지만 근거가 약함
rationale에 불확실성 원인을 포함하도록 prompt에서 지시함
=====
 10. Stage 1.5 - ai_readable 힌트 생성
=====


관련 함수:

build_ai_readable_hints_for_set


사용 prompt:

MAKE_AI_READABLE_HINTS_FOR_SET_PROMPT


역할:
각 Join 후보 세트에 대해 질문 생성에 도움이 되는 해석 포인트를 추출한다.
이 단계에서 추출하는 정보는 다음과 같다.

status_or_flag_points

상태, 여부, 플래그 성격의 컬럼 및 값
예: Y/N, 완료/진행, 활성/비활성 등

code_mapping_points

코드값이나 약어를 자연어로 바꿀 수 있는 포인트
예: CD, TYPE, STATUS 등

business_term_points

컬럼명만으로는 의미가 부족하고 설명을 봐야 이해되는 업무 용어

ambiguous_column_points

서로 혼동될 수 있는 컬럼들
예: 생성일/등록일/적용일/수정일
예: 판매금액/매출금액/청구금액

join_enrichment_points

다른 테이블의 속성이나 분류 정보가 있어야 자연스러운 질문이 되는 포인트

recommended_question_types

해당 세트에서 만들기 좋은 질문 유형


이 힌트는 Stage 2 질문 생성 prompt에 입력되어, ai_readable 효과가 잘 드러나는 질문을 생성하는 데 사용된다.

=====
 11. Stage 2 - 질문 및 semantic_form 생성
=====


관련 함수:

make_nl2sql_questions_multi_table
generate_one_round_questions_with_gold_and_rewrite


사용 prompt:

MAKE_MULTI_TABLE_QUESTIONS_PROMPT


역할:
LLM이 테이블 정보, 조인 후보, ai_readable 힌트를 바탕으로 자연어 질문과 semantic_form을 생성한다.
생성되는 질문은 단순 조회가 아니라 NL2SQL 평가에 적합한 분석형 질문을 목표로 한다.
질문 생성 시 중요한 원칙은 다음과 같다.

최소 테이블 사용 원칙
입력에 여러 테이블이 있어도 실제 정답에 필요한 최소 테이블만 사용한다.
단일 테이블로 답할 수 있는 질문은 JOIN을 만들지 않는다.
두 개 이상의 테이블이 반드시 필요할 때만 JOIN을 사용한다.
needed_tables는 실제 필요한 테이블만 포함해야 한다.
user_question의 [TABLES: ...] 접두어와 needed_tables는 동일해야 한다.
ai_readable 민감 질문 우선


단순 컬럼명 매칭만으로 풀 수 있는 질문보다, 컬럼 설명/값 예시/업무 의미가 있어야 정확히 풀 수 있는 질문을 우선 생성한다.
주요 질문 유형은 다음과 같다.

status_interpretation

상태값, 여부값, 플래그값을 자연어로 해석해야 하는 질문
예: 완료된, 진행 중인, 전송된, 미전송된, 활성인

code_to_nl_mapping

DB에는 코드로 저장되어 있지만 질문은 자연어로 표현하는 질문
예: value는 Y이지만 질문은 “사용 중인”으로 표현

business_term_mapping

업무 용어와 실제 컬럼/값 사이에 해석이 필요한 질문

ambiguous_column_resolution

유사한 컬럼 중 정확한 컬럼을 선택해야 하는 질문
예: 생성일, 등록일, 적용일 중 어떤 컬럼을 써야 하는지

ratio_definition

분자/분모 정의가 중요한 비율/점유율/성공률 질문

dimension_enrichment_join

다른 테이블의 속성/분류가 있어야 성립하는 JOIN 질문

join_group_analysis

JOIN 후 차원 기준으로 그룹 집계하는 질문

join_filter_enrichment

다른 테이블 속성값으로 필터링하는 질문

join_topk_by_dimension

다른 테이블의 분류 기준으로 상위 N개를 구하는 질문

join_ratio

JOIN 기반 비율 계산 질문
너무 쉬운 질문 금지


다음과 같은 질문은 생성하지 않도록 prompt와 후처리 필터에서 제어한다.

단일 조건만 있는 단순 COUNT 질문
단순 목록 조회
DISTINCT 목록 조회
필터 1개 + 원시 컬럼 1개 조회
정적 마스터 조회
“모두 알려줘”, “목록 보여줘” 유형의 단순 열람 질문
필터 값 규칙


WHERE 조건에 사용하는 값은 반드시 tables_blob의 값 예시에 실제 존재하는 값을 사용해야 한다.
금지 표현은 다음과 같다.

특정
임의
아무
어떤
예시
sample
unknown
YYYY
XXXX


semantic_form.filters.value에는 실제 저장값을 그대로 넣어야 한다.
예를 들어 질문에는 “완료된”이라고 쓰더라도, 실제 저장값이 COMPLETE이면 semantic_form에는 COMPLETE를 넣는다.

날짜/시간 규칙


값 예시가 ISO 날짜나 timestamp 형태일 경우, 질문에는 자연어 날짜 표현으로 바꿔 쓸 수 있다.
하지만 semantic_form.filters.value에는 원본 값을 그대로 유지해야 한다.
예시:

질문 표현: 2025년 11월 4일에 수집된 데이터
semantic_form value: 2025-11-04
GROUP BY 규칙


group_by가 있으면 SELECT의 비집계 컬럼은 반드시 group_by에 포함되어야 한다.
비율 계산도 집계 후 계산 형태로 생성해야 한다.
예:

잘못된 방식: a.amount / b.total_amount
올바른 방식: SUM(a.amount) / SUM(b.total_amount)
나눗셈 안전 규칙


분모가 0일 수 있는 비율 계산은 dialect별 안전 처리를 해야 한다.

BigQuery: SAFE_DIVIDE 사용
PostgreSQL: NULLIF 사용

 12. semantic_form 구조
=====


semantic_form은 질문 의도를 구조화한 JSON이다.
기본 구조는 다음과 같다.

select

조회할 컬럼 또는 집계식

group_by

그룹 기준 컬럼

filters

WHERE 조건

order_by

정렬 기준

joins

semantic_form은 gold_sql 생성의 절대 기준이다.
즉, gold_sql 생성 prompt에서는 user_question보다 semantic_form을 우선하도록 지시되어 있다.

 13. Stage 2 후처리 - 질문 필터링
=====


질문 생성 후 여러 필터를 적용하여 품질이 낮은 질문을 제거한다.
관련 함수는 다음과 같다.

normalize_question_schema
normalize_question_types
semantic_form_has_groupby_violation
has_unnecessary_join
needed_tables_mismatch
join_used_mismatch
is_trivial_question
is_ai_readable_insensitive_question
filter_questions_before_gold_sql_semantic_only_debug


주요 필터링 기준은 다음과 같다.

needed_columns 스키마 정규화


needed_columns는 반드시 객체 배열이어야 한다.
정상 형태:

table: 테이블명
column: 컬럼명


LLM이 문자열 리스트 형태로 잘못 반환하면 안전하게 빈 리스트로 초기화한다.

GROUP BY 위반 제거


group_by가 있는데 SELECT에 비집계 컬럼이 포함되거나, 집계 함수 없이 expression을 사용하는 경우 제거한다.

불필요한 JOIN 제거


JOIN이 존재하지만 실제 select/filter/group/order에서 한 테이블만 사용하는 경우 제거한다.

needed_tables 불일치 제거


semantic_form에서 실제 사용한 테이블이 needed_tables에 포함되지 않으면 제거한다.

join_used 불일치 제거


semantic_form.joins에는 JOIN이 있는데 join_used가 비어 있거나, 반대로 join_used는 있는데 semantic_form.joins가 비어 있으면 제거한다.

trivial question 제거


다음 유형은 제거한다.

단순 count
단순 raw column lookup
단순 목록 조회
ai_readable 민감도가 낮은 질문 제거


컬럼 설명이나 값 해석이 없어도 쉽게 풀 수 있는 질문은 제거한다.

필터 값 검증


filter 값에 placeholder가 포함되어 있거나 value_evidence가 없으면 제거한다.
현재 설정에서는 value_evidence를 필수로 요구한다.

=====
 15. SQL Dialect별 테이블명 규칙
=====
BigQuery

BigQuery로 gold_sql을 생성할 때 FROM/JOIN에 사용되는 테이블명은 반드시 다음 형식을 따라야 한다.
형식:
FROM pjt-lge-edl-ob.OB_00006.TABLE_NAME
규칙:

backtick을 반드시 사용한다.
프로젝트/데이터셋 prefix는 고정값을 사용한다.
고정 prefix: pjt-lge-edl-ob.OB_00006.
테이블명은 반드시 대문자로 작성한다.
예: v_newgdmi_sample_table 이라는 테이블은 SQL에서 V_NEWGDMI_SAMPLE_TABLE 로 사용한다.


예시:
SELECT a.COL1, COUNT(*) AS cnt FROM pjt-lge-edl-ob.OB_00006.V_NEWGDMI_SAMPLE_TABLE a GROUP BY a.COL1
BigQuery 테이블명 규칙 검증 함수:

bigquery_sql_has_valid_prefix_and_upper_tables


이 함수는 gold_sql의 FROM/JOIN에 등장하는 테이블이 다음 조건을 만족하는지 확인한다.

backtick으로 감싸져 있는지
pjt-lge-edl-ob.OB_00006. prefix를 사용하는지
prefix 뒤의 테이블명이 대문자인지
PostgreSQL


PostgreSQL로 gold_sql을 생성할 때 FROM/JOIN에 사용되는 테이블명은 반드시 다음 형식을 따라야 한다.
형식:
FROM ic360prd.ic360_encrypt_l2.table_name
규칙:

3파트 backtick 형식을 사용한다.
첫 번째 파트는 ic360prd
두 번째 파트는 ic360_encrypt_l2
세 번째 파트는 semantic_form에 나온 테이블명을 그대로 사용한다.


예시:
SELECT a.col1, COUNT(*) AS cnt FROM ic360prd.ic360_encrypt_l2.v_newgdmi_sample_table a GROUP BY a.col1
PostgreSQL 테이블명 규칙 검증 함수:

postgres_sql_has_required_3part_backtick


이 함수는 gold_sql의 FROM/JOIN 테이블 참조가 다음 형식인지 확인한다.

ic360prd.ic360_encrypt_l2.<table>
=====
 16. V_L0 / V_LO 테이블명 오타 보정
=====


관련 함수:

sql_has_v_lo_typo
fix_v_lo_to_v_l0


역할:
LLM이 테이블명을 생성할 때 숫자 0을 알파벳 O로 잘못 쓰는 경우가 있다.
예를 들어 실제 테이블명이 V_L0EAPP... 인데, LLM이 V_LOEAPP... 처럼 생성할 수 있다.
이 문제를 방지하기 위해 gold_sql 생성 후 다음 처리를 수행한다.

SQL에 V_LO 형태가 있는지 검사한다.

발견되면 V_L0로 자동 치환한다.

치환 후에도 V_LO가 남아 있으면 해당 SQL은 unanswerable로 처리한다.


예시:

잘못된 형태: V_LOEAPP_SAMPLE
올바른 형태: V_L0EAPP_SAMPLE


이 처리는 BigQuery와 PostgreSQL 모두에서 사용된다.

=====
 17. Stage 4 - 질문 리라이팅
=====


관련 함수:

extract_keywords_with_llm
rewrite_questions_softly


사용 prompt:

MAKE_PURPOSE_KEYWORDS_PROMPT
MAKE_SOFTEN_QUESTION_PROMPT


역할:
LLM이 최초 생성한 질문을 실제 업무 사용자가 묻는 것처럼 더 자연스럽게 바꾼다.
이 단계에서는 질문의 의미, 조건, 필터 값, 집계 기준, 정렬 기준 등을 바꾸면 안 된다.
오직 문장 표현만 자연스럽게 수정한다.
처리 흐름은 다음과 같다.

해당 질문에 사용된 테이블들의 목적 설명을 수집한다.

테이블 목적 설명에서 업무 맥락 키워드와 대상 키워드를 추출한다.

추출된 키워드를 활용해 질문을 자연스럽게 리라이팅한다.

[TABLES: ...] 접두어는 제거한다.

결과를 user_question_final 컬럼에 저장한다.


추출하는 키워드 종류는 다음과 같다.

context_keywords


업무, 도메인, 프로세스 맥락을 나타내는 키워드다.
예:

전사 수요관리
제품 개발
공급 관리
케어솔루션
마켓 데이터
entity_keywords


질문 대상이나 주요 개체를 나타내는 키워드다.
예:

제품
모델
고객
주문
프로젝트
사업부


리라이팅 예시는 다음과 같다.
원본 질문:
[TABLES: v_xxx] 2025년 1월 완료된 요청 건수를 상태별로 알려줘
리라이팅 결과:
전사 수요관리 업무에서 2025년 1월 완료된 요청 건수를 상태별로 알려줘
주의사항:

리라이팅 결과가 원문과 거의 동일하면 변경하지 않는다.
context_keywords가 있는 경우, 리라이팅 결과에 가능한 한 해당 키워드를 포함하도록 한다.
의미가 바뀔 가능성이 있으면 원문을 유지한다.

 18. Stage 4.5 - 코드값/저장값 자연어화
=====


관련 함수:

rewrite_questions_remove_codes

REWRITE_QUESTION_REMOVE_CODES_PROMPT


역할:
질문에 남아 있는 DB 내부 코드값, 약어, 저장값을 자연스러운 한국어 표현으로 바꾼다.
이 단계는 ai_readable 평가 효과를 높이기 위해 중요하다.
NL2SQL 모델이 단순히 질문에 있는 코드값을 그대로 WHERE 조건에 넣는 것이 아니라, 자연어 표현을 보고 적절한 실제 저장값을 찾아야 하기 때문이다.
예시는 다음과 같다.

Y/N 값 자연어화
Y -> 사용 중인
Y -> 활성인
Y -> 전송된
Y -> 적용된
N -> 사용하지 않는
N -> 비활성인
N -> 전송되지 않은
N -> 미적용된
상태 코드 자연어화
COMPLETE -> 완료된
COMP -> 완료된
ING -> 진행 중인
PROGRESS -> 진행 중인
CLOSED -> 종료된
NEW -> 신규 상태의
번호 + 명칭 형태 자연어화
아시아 -> 아시아
유럽 -> 유럽
북미 -> 북미
업무 코드 자연어화


컬럼 설명과 값 예시를 보고 의미가 명확한 경우에만 자연어로 바꾼다.
의미가 불확실한 코드는 원문 값을 유지한다.

1순위: user_question_final2
2순위: user_question_final
3순위: user_question

 19. Stage 5 - SQL 논리 검증
=====


관련 함수:

validate_sql_with_catalog

SQL_VALIDATE_PROMPT


역할:
생성된 gold_sql이 질문 의도와 semantic_form에 맞는지 LLM validator로 검증한다.
검증 입력은 다음과 같다.

사용자 질문
semantic_form
테이블 카탈로그
gold_sql


검증 결과는 O 또는 X로 나온다.
O는 SQL이 맞다는 의미다.
X는 SQL이 틀렸다는 의미다.
검증 결과 예시는 다음과 같다.
{"Result": ["O", "정확한 테이블과 컬럼을 사용했고 필터 및 집계 로직이 질문 의도와 일치합니다."]}
{"Result": ["X", "질문은 사업부별 집계를 요구하지만 SQL에 GROUP BY가 없어 전체 합계만 반환합니다."]}
검증 기준은 다음과 같다.

논리적 정확성만 평가한다.
DB prefix 차이는 오류로 보지 않는다.
테이블/컬럼명의 대소문자 차이는 오류로 보지 않는다.
카탈로그에 없는 테이블이나 컬럼을 사용하면 X로 판단한다.
JOIN 조건이 잘못되었으면 X로 판단한다.
WHERE 조건이 semantic_form과 다르면 X로 판단한다.
GROUP BY 기준이 질문 의도와 다르면 X로 판단한다.
집계 방식이 질문 의도와 다르면 X로 판단한다.
user_question이 애매하면 semantic_form을 우선 기준으로 판단한다.

 20. Stage 5.5 - SQL Repair
=====


관련 함수:

repair_gold_sql_with_reason


사용 prompt:

REPAIR_GOLD_SQL_PROMPT


역할:
SQL 검증 결과가 X인 경우, validator가 제공한 실패 사유를 바탕으로 SQL을 수정한다.
repair의 기준도 semantic_form이다.
즉, user_question보다 semantic_form을 우선으로 보고 SQL을 고친다.
repair prompt에 전달되는 정보는 다음과 같다.

user_question
semantic_form
table_catalog
current_sql
validator_reason
dialect


repair 결과는 다음 형태로 반환된다.

status

ok 또는 unanswerable

repaired_sql

수정된 SQL

changes

어떤 점을 수정했는지에 대한 설명


현재 validate_questions_list 함수에서는 다음 설정으로 repair를 수행한다.

enable_repair = True
repair_max_attempts = 1


즉, 1차 검증에서 충분한 O 질문을 확보하지 못하면 X 질문에 대해 1회 repair를 시도한다.
repair 후에는 다시 SQL 검증을 수행한다.
repair된 SQL도 O 판정을 받아야 최종 후보로 남는다.

=====
 21. Stage 5.6 - Semantic Form Repair
=====


관련 함수:

repair_semantic_form_to_match_sql


사용 prompt:

REPAIR_SEMANTIC_FORM_PROMPT


역할:
SQL repair 이후 SQL은 맞게 되었지만 기존 semantic_form과 SQL 구조가 달라질 수 있다.
이 경우 현재 SQL에 맞도록 semantic_form을 최소 수정한다.
semantic_form repair의 목적은 다음과 같다.

gold_sql과 semantic_form의 불일치 해소
최종 평가셋에서 질문, semantic_form, gold_sql의 정합성 유지


semantic_form repair 원칙은 다음과 같다.

table_catalog에 있는 테이블/컬럼만 사용한다.
current_sql의 SELECT, WHERE, JOIN, GROUP BY, ORDER BY, LIMIT 구조와 일치하도록 수정한다.
질문 의미를 바꾸는 과도한 수정은 금지한다.
질문 의미와 SQL이 심각하게 충돌하면 unanswerable로 처리한다.


현재 설정에서는 semantic_form repair 후 SQL을 다시 생성하고, 다시 검증한다.
관련 옵션은 다음과 같다.

enable_semantic_repair = True
semantic_repair_regen_sql = True
semantic_repair_drop_if_fail = True

 27. 실행 결과 로그에서 확인할 주요 메시지
=====


실행 중 console에 여러 로그가 출력된다.
주요 로그 의미는 다음과 같다.

[PURPOSE-GROUP]


목적 기반 테이블 그룹이 몇 개 생성되었는지 보여준다.
예:
[PURPOSE-GROUP] n_groups=8

[SET]


candidate set별 질문 생성 라운드를 보여준다.
예:
[SET] set_id=s01 round=1 need_more=2 gen_n=16 tables=[...]
의미:

set_id: 현재 처리 중인 join candidate set
round: 재생성 라운드 번호
need_more: 이 set에서 추가로 필요한 질문 개수
gen_n: 이번 라운드에서 LLM에게 생성 요청한 질문 수
tables: 현재 set의 테이블 목록
[SEMANTIC-FILTER]


semantic_form 구조나 질문 품질 문제로 제거된 질문 수를 보여준다.
예:
[SEMANTIC-FILTER] dropped={'groupby_violation': 1, 'unnecessary_join': 2}

[FILTER-DEBUG]


필터 값 검증 결과를 보여준다.
예:
[FILTER-DEBUG] total=12 kept=8 dropped=4 top=[...]

[SQL-VALIDATE]


SQL 검증 결과를 보여준다.
예:
[SQL-VALIDATE] set_id=s01 round=1 counts={'O_firstpass': 2, 'X_firstpass': 3}

[SQL-VALIDATE] X reason top


SQL 검증 실패 사유 상위 목록을 보여준다.

[SYSTEM-CHECK]


시스템 전체 pool 상태를 보여준다.
예:
[SYSTEM-CHECK] pool_size=8 join_count=3 distinct_sets=5
의미:

pool_size: 현재까지 확보한 전체 질문 수
join_count: JOIN 질문 수
distinct_sets: 질문이 나온 candidate set의 개수
[SYSTEM] stop


목표 질문 수, JOIN 질문 수, set 다양성 조건을 만족하여 생성을 종료했다는 의미다.

[DONE]


해당 시스템의 Excel 저장이 완료되었다는 의미다.
예:
[DONE] New GDMi(전사수요관리시스템) -> /path/question_260421_New GDMi(...).xlsx rows=10

 28. 에러 발생 시 확인 포인트
=====
Azure OpenAI 환경변수 오류


증상:

OPENAI_API_KEY 관련 KeyError
Azure endpoint 오류
deployment name 오류


확인할 것:

.env 파일 존재 여부
OPENAI_API_KEY
OPENAI_API_VERSION
DEPLOYMENT_NAME
AZURE_OPENAI_ENDPOINT
LLM 응답 JSON parsing 오류


증상:

output is not valid JSON
No '{' found in text
json.JSONDecodeError


원인:

LLM이 JSON 이외의 설명을 섞어서 응답
코드펜스 형식이 깨짐
응답이 중간에 잘림


관련 방어 함수:

_strip_code_fences
_extract_first_json_object


대응:

동일 cell 재실행
prompt 수정
max_tokens 설정 확인
LLM 응답 raw 확인
질문이 너무 적게 생성되는 경우


가능한 원인:

필터링 조건이 강함
value_evidence가 누락됨
SQL validator에서 X가 많이 발생
repair 실패
join candidate set 품질이 낮음


조정 가능한 파라미터:

regen_max_rounds 증가
stage2_oversample_factor 증가
n_candidate_sets 증가
questions_per_set 증가
enable_value_filtering 완화
join_question_ratio 조정
JOIN 질문이 부족한 경우


가능한 원인:

join candidate set의 confidence가 낮음
실제 조인 가능한 테이블이 적음
불필요한 join 필터에서 제거됨
SQL validator에서 join SQL이 X 처리됨


관련 로직:

prefer_join_questions
select_questions_with_soft_join_quota
select_questions_with_hard_min_join_quota




조정 가능한 값:

join_question_ratio 증가

JOIN 질문을 더 많이 만들도록 Stage 2 prompt에 전달하는 비율을 높인다.
예: 50 -> 70

n_candidate_sets 증가

더 많은 join candidate set을 생성하게 해서 JOIN 질문 후보 풀을 넓힌다.
예: 10 -> 15 또는 20

questions_per_set 증가

각 candidate set에서 확보하려는 질문 수를 늘린다.
예: 2 -> 3

total_target_questions 증가

시스템 전체 목표 질문 수를 늘려 최종 pool이 더 커지게 한다.
단, 최종 평가셋 크기도 같이 늘어난다.

regen_max_rounds 증가

질문 생성/검증 라운드를 더 많이 반복한다.
JOIN 질문이 validator에서 많이 탈락할 때 도움이 된다.
예: 8 -> 10 또는 12

stage2_oversample_factor 증가

필요한 개수보다 더 많은 질문을 생성하게 한다.
필터링과 SQL 검증에서 많이 탈락하는 경우 도움이 된다.
예: 5.0 -> 7.0


주의사항:

join_question_ratio를 너무 높이면 LLM이 불필요한 JOIN을 억지로 만들 수 있다.
불필요한 JOIN은 has_unnecessary_join 필터에서 제거된다.
따라서 JOIN 질문 수를 늘릴 때는 join_question_ratio만 올리기보다 n_candidate_sets와 stage2_oversample_factor도 함께 조정하는 것이 좋다.
gold_sql이 unanswerable로 많이 떨어지는 경우


가능한 원인:

semantic_form이 불완전함
semantic_form에 카탈로그에 없는 컬럼이 포함됨
user_question에 “특정”, “임의”, “어떤” 같은 placeholder 표현이 남아 있음
필터 value가 실제 값 예시에 없는 값임
LLM이 테이블 prefix 규칙을 지키지 않음
BigQuery/PostgreSQL dialect 규칙을 혼동함
GROUP BY 규칙 위반
JOIN 조건이 불명확함


관련 함수:

generate_gold_sql_for_questions
generate_gold_sql_single
semantic_form_has_groupby_violation
filter_questions_before_gold_sql_semantic_only_debug
bigquery_sql_has_valid_prefix_and_upper_tables
postgres_sql_has_required_3part_backtick


확인할 것:

semantic_form의 select, filters, joins가 정상인지 확인한다.
filters.value가 tables_blob의 값 예시에 실제로 존재하는지 확인한다.
user_question에 placeholder 표현이 남아 있는지 확인한다.
gold_sql_status가 unanswerable인 row의 gold_sql_rationale을 확인한다.
BigQuery 실행 시 테이블명이 대문자이고 prefix가 맞는지 확인한다.
PostgreSQL 실행 시 3파트 backtick 형식이 맞는지 확인한다.


조정 가능한 값:

enable_value_filtering을 True로 유지한다.

필터 값 문제가 있는 질문을 gold_sql 생성 전에 제거할 수 있다.

stage2_oversample_factor를 증가시킨다.

더 많은 질문을 생성해서 gold_sql 생성 성공 후보를 늘린다.

regen_max_rounds를 증가시킨다.

여러 라운드 재생성을 통해 충분한 질문을 확보한다.

prompt의 필터 값 규칙을 더 강하게 수정한다.

value_evidence에 반드시 값 출처를 쓰도록 유도한다.


주의사항:

gold_sql이 unanswerable로 많이 떨어진다고 해서 무조건 repair에 의존하면 안 된다.
semantic_form 자체가 잘못된 경우 SQL repair만으로는 품질이 좋아지지 않는다.
가능하면 Stage 2 질문 생성 prompt와 semantic filter에서 불량 질문을 먼저 줄이는 것이 좋다.
SQL Validator에서 X가 많이 발생하는 경우


가능한 원인:

gold_sql이 semantic_form과 다름
SELECT 집계식이 질문 의도와 다름
GROUP BY 기준이 누락됨
WHERE 조건이 semantic_form과 다름
JOIN 조건이 부정확함
ORDER BY 또는 LIMIT 사용이 부적절함
ratio 계산식에서 분자/분모가 잘못됨
카탈로그에 없는 컬럼을 사용함


관련 함수:

validate_sql_with_catalog
validate_questions_list
repair_gold_sql_with_reason
repair_semantic_form_to_match_sql


확인할 것:

SQL_VALIDATE 로그의 X reason top을 확인한다.
X samples에 출력되는 user_question, reason, sql_head를 확인한다.
semantic_form과 gold_sql을 비교한다.
gold_sql이 semantic_form 기준으로 작성되었는지 확인한다.
JOIN SQL의 ON 조건이 join_key_candidates 또는 semantic_form.joins와 일치하는지 확인한다.


조정 가능한 값:

repair_max_attempts 증가

현재는 1회만 repair한다.
필요 시 2회로 늘릴 수 있다.
단, LLM 호출 비용과 시간이 증가한다.

enable_semantic_repair 유지

SQL repair 후 semantic_form과 gold_sql이 어긋나는 문제를 줄인다.

semantic_repair_regen_sql 유지

수정된 semantic_form 기준으로 SQL을 다시 생성해 정합성을 높인다.


주의사항:

validator도 LLM이므로 완벽하지 않다.
애매한 경우 O로 판단하도록 prompt에 지시되어 있지만, 실제로는 보수적으로 X를 줄 수도 있다.
대량 생성 후 샘플링 검수를 통해 validator 판단 품질을 확인하는 것이 좋다.
JSON parsing 오류가 자주 발생하는 경우


가능한 원인:

LLM이 JSON 외 설명을 같이 출력함

ExampleJSON
 
undefined

응답 앞뒤에 문장이 섞임
응답이 길어서 중간에 잘림
JSON 내부 따옴표 escape가 깨짐


관련 함수:

_strip_code_fences
_extract_first_json_object


현재 방어 로직:

코드펜스가 있으면 내부 JSON만 추출한다.
응답 내 첫 번째 JSON object를 찾아 파싱한다.
그래도 실패하면 ValueError 또는 unanswerable로 처리한다.


확인할 것:

오류 메시지에 포함된 RAW 응답을 확인한다.
LLM 응답이 실제 JSON 형식인지 확인한다.
prompt의 “출력은 반드시 JSON만” 지시가 유지되어 있는지 확인한다.


대응 방법:

동일 시스템 재실행
prompt에 “설명 금지, JSON만 출력” 문구 강화
생성 개수 gen_n을 줄여 응답 길이를 줄임
너무 많은 테이블/컬럼이 prompt에 들어가지 않도록 max_tables_in_stage1_prompt 조정
필요 시 max_col_width를 줄여 prompt 길이 축소
Rate limit 또는 timeout이 발생하는 경우


가능한 원인:

max_workers가 너무 큼
시스템 수가 많음
각 시스템에서 LLM 호출이 많음
regen_max_rounds가 큼
stage2_oversample_factor가 큼
SQL validation과 repair까지 수행하여 호출량이 증가함


관련 설정:

max_workers
regen_max_rounds
stage2_oversample_factor
n_candidate_sets
questions_per_set
total_target_questions
repair_max_attempts


대응 방법:

max_workers를 줄인다.

현재: 10
권장 시작값: 3
안정화 후 5 정도까지 증가

regen_max_rounds를 줄인다.

예: 8 -> 5

stage2_oversample_factor를 줄인다.

예: 5.0 -> 3.0

n_candidate_sets를 줄인다.

예: 10 -> 6

repair_max_attempts를 1로 유지한다.

2 이상으로 올리면 호출량이 크게 늘어난다.


주의사항:

병렬 처리 수를 높이면 전체 시간은 줄어들 수 있지만, Azure OpenAI rate limit에 걸릴 가능성이 커진다.
여러 시스템을 동시에 돌릴 때는 max_workers를 낮추는 것이 안전하다.

 29. 주요 파라미터 튜닝 가이드
=====
최종 질문 수를 늘리고 싶을 때


수정 대상:

total_target_questions
n_candidate_sets
questions_per_set


예시:
현재 설정:

n_candidate_sets = 10
questions_per_set = 2
total_target_questions = 10


질문 수를 20개로 늘리고 싶으면 예를 들어 다음처럼 조정할 수 있다.

n_candidate_sets = 15
questions_per_set = 3
total_target_questions = 20


주의사항:

total_target_questions만 늘리면 후보 pool이 부족할 수 있다.
n_candidate_sets와 questions_per_set도 함께 조정하는 것이 좋다.
품질을 우선하고 싶을 때


수정 대상:

stage2_oversample_factor 증가
regen_max_rounds 증가
enable_value_filtering True 유지
enable_question_rewrite True 유지
SQL validation 유지
repair 유지


추천 예시:

stage2_oversample_factor = 5.0 이상
regen_max_rounds = 8 이상
enable_value_filtering = True
enable_question_rewrite = True


장점:

필터링 후에도 좋은 후보가 남을 가능성이 높다.
SQL 검증 O 질문 위주로 최종 선별된다.


단점:

LLM 호출량 증가
실행 시간 증가
비용 증가
실행 시간을 줄이고 싶을 때


수정 대상:

n_candidate_sets 감소
regen_max_rounds 감소
stage2_oversample_factor 감소
total_target_questions 감소
max_workers 조정
repair 비활성화 고려


예시:

n_candidate_sets = 6
questions_per_set = 2
total_target_questions = 8
regen_max_rounds = 4
stage2_oversample_factor = 3.0


주의사항:

실행 시간은 줄어들지만 최종 질문 품질과 다양성이 낮아질 수 있다.
SQL validation을 끄는 것은 권장하지 않는다.
ai_readable 효과가 강한 질문을 더 많이 만들고 싶을 때


관련 로직:

ai_readable_hints
ai_readable_sensitivity_score
is_ai_readable_insensitive_question
generation_mode = ai_readable_sensitive
rewrite_questions_remove_codes


조정 방향:

generation_mode를 ai_readable_sensitive로 유지한다.
enable_question_rewrite를 True로 유지한다.
is_ai_readable_insensitive_question 필터를 유지한다.
최종 선별 시 ai_readable_sensitivity_score가 높은 질문을 우선 선택한다.


질문 유형 예시:

상태값 해석 질문
Y/N 플래그 자연어 질문
코드값을 자연어로 표현한 질문
유사 컬럼 중 정확한 의미를 골라야 하는 질문
비율/점유율처럼 정의가 중요한 질문
다른 테이블의 속성/분류가 필요한 JOIN 질문


주의사항:

질문에 코드값이 그대로 노출되면 ai_readable 효과가 약해진다.
따라서 rewrite_questions_remove_codes 단계가 중요하다.
JOIN 질문 비중을 늘리고 싶을 때


수정 대상:

join_question_ratio 증가
n_candidate_sets 증가
stage2_oversample_factor 증가
per_set_min_join 조정
final_min_join_required 조정


현재 코드 일부 로직:

high 또는 medium confidence set에서는 per_set_min_join을 2로 설정한다.
시스템 최종 선별에서는 최소 3개까지 JOIN 질문 확보를 시도한다.


수정 예시:

join_question_ratio = 70
final_min_join_required = min(5, final_target_n)


주의사항:

JOIN 질문을 억지로 늘리면 불필요한 JOIN이 증가한다.
불필요한 JOIN은 필터에서 제거되거나 validator에서 X가 될 가능성이 높다.
따라서 조인 후보 세트 품질이 더 중요하다.
SQL 정답 품질을 더 엄격하게 관리하고 싶을 때


권장 설정:

enable_sql_validation = True
enable_repair = True
enable_semantic_repair = True
semantic_repair_regen_sql = True
semantic_repair_drop_if_fail = True


추가로 고려할 수 있는 것:

validator prompt를 더 엄격하게 수정
validate_sql_with_catalog 결과가 X인 경우 샘플 저장
gold_sql_status가 unanswerable인 케이스 별도 저장
최종 Excel에 sql_validation_reason 컬럼 추가


주의사항:

현재 extract_qa_pairs_from_result에서는 최종 Excel에 validation reason을 포함하지 않는다.
디버깅 목적으로 필요하면 extract 함수에 컬럼을 추가하면 된다.
